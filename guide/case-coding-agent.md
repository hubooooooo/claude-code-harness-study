# 案例：研发团队引入编程 Agent

前两个案例都要自己搭 Agent。这个案例走的是另一条路：**直接买现成的产品**。

很多人以为买了成品，产品经理就没事可做了。恰恰相反：成品自带了全套部件，但每个部件「怎么配置」，比如什么能做、什么不能做、记录什么，仍然要有人拍板。这就是这个案例里产品经理的工作。

---

## 1. 背景

一家做企业软件的公司，研发团队 80 人。CTO 想引入 AI 编程 Agent 提升研发效率，让负责研发效能的产品经理牵头评估和推广。

已知条件：

| 条件 | 情况 |
|---|---|
| 代码 | 公司的核心资产，安全团队对代码外流很敏感 |
| 环境 | 生产环境里有客户数据，研发人员的电脑上有部分配置和密钥 |
| 现状 | 已经有少数工程师自己掏钱在用各种 AI 编程工具，没有统一管理 |
| 目标 | 统一选型、统一配置，三个月内让大部分工程师用起来，同时不出安全事故 |

注意第三条：**员工已经在私下用了。** 不统一管理，风险反而更大。

---

## 2. 先问：真的需要 Agent 吗？

写代码、修 bug、补测试，都是「做一步、看结果、再决定下一步」：改完要跑测试，测试失败了要看报错再改。这是 Agent 最典型、也最成熟的场景。

**结论：需要。** 这一步不用花太多时间。

---

## 3. 走哪条路？

| 问题 | 这个案例的回答 | 指向 |
|---|---|---|
| ① 真的需要 Agent 吗 | 需要 | 继续 |
| ② 内部提效还是做进产品 | 内部提效，而且写代码正是现成产品最擅长的 | **直接用成品** |
| ③～⑤ | 用成品时，这几个问题变成了「选哪家成品」的评估维度 | 见下表 |

**结论：直接用成品。** 自己搭一个编程 Agent，做得再好，也很难追上专门做这件事的厂商的迭代速度。

### 选哪一家：评估维度

市面上的编程 Agent 更新很快，名单每个季度都在变。比起记住哪家好，更重要的是知道**拿什么去比**：

| 要问的问题 | 为什么重要 | 对应的部件 |
|---|---|---|
| 能不能由管理员统一下发权限规则，员工改不掉 | 安全底线不能靠每个人自觉 | s03 权限 |
| 能不能在执行前后挂上公司自己的检查和审计 | 安全团队要能看到 Agent 做了什么 | s04 钩子 |
| 能不能写团队共享的项目说明，让 Agent 遵守代码规范 | 不然每个人都要反复交代 | s07 技能、s09 记忆 |
| 能不能接内部系统，接入能不能由管理员控制 | 接工单、接文档才能真正融进工作流 | s14 MCP |
| 代码会不会被拿去训练、在厂商那里保存多久 | 安全团队最关心的问题 | — |
| 用在命令行、编辑器，还是云端 | 影响工程师的使用习惯和推广难度 | — |
| 按人收费还是按用量收费，有没有费用上限 | 预算可控 | s01 循环的费用上限 |

**做法**：挑两三家，每家找一个小组试用两周，用同一张表打分，再加上工程师的主观评价。不要只看演示视频和评测榜单。

---

## 4. 逐个部件：成品已经自带，你要定的是配置

| 部件 | 成品里是什么样 | 我们的配置决定 |
|---|---|---|
| s01 循环 | 自带 | 设个人每月费用上限，超了要申请 |
| s02 工具 | 自带读写文件、搜索、执行命令 | 不额外限制，交给权限来管 |
| s03 权限 | 自带多种模式和规则 | **这是配置的重点**，见下面的三档清单 |
| s04 钩子 | 大多数成品支持 | 记录 Agent 执行的每条命令，交给安全团队；提交代码前自动扫描有没有夹带密钥 |
| s05 待办、s06 子 Agent、s08 压缩 | 自带 | 不用管，用默认设置 |
| s07 技能、s09 记忆 | 自带项目说明文件 | 每个代码仓库放一份项目说明：代码规范、架构说明、测试怎么跑。由各组技术负责人维护，和代码一起评审 |
| s11 后台、云端任务 | 部分成品支持把任务放到云端跑 | **试点期不开放**。代码在云端运行，涉及另一套数据安全评估 |
| s13 团队 | 部分成品有实验功能 | 不推广，等成熟了再说 |
| s14 MCP | 自带 | 白名单：内部文档、工单系统，只读。禁止接生产数据库 |
| s17 目标判断 | 部分成品支持 | 用公司现有的流程代替：**Agent 写的代码和人写的代码一样，必须通过自动测试和人工代码评审才能合并** |

**权限三档清单**：

| 档位 | 操作 |
|---|---|
| **直接放行** | 读代码、搜索、跑测试、在本地分支上改代码 |
| **先问人（使用者本人确认）** | 安装新的依赖包、执行网络请求、删除文件 |
| **绝对禁止（管理员统一下发，员工改不掉）** | 读取密钥和配置文件、强制覆盖远程代码、连接生产环境、直接合并到主分支 |

最后一条规则值得单独说：**Agent 出错不可怕，可怕的是错误绕过了原本就有的把关流程。** 只要代码评审和自动测试这两道关还在，Agent 写错的代码就和新人写错的代码一样，会被拦下来。

---

## 5. 规则清单

| 类别 | 规则 |
|---|---|
| 统一管理 | 只允许使用公司选定的工具和公司账号；个人账号停用 |
| 权限 | 按三档清单，由管理员统一下发 |
| 代码质量 | Agent 参与的代码照常走测试和评审；评审人对合并的代码负责，不能说「是 AI 写的」 |
| 数据 | 确认厂商的企业版条款：代码不用于训练；保存时间符合安全要求 |
| 审计 | Agent 执行的命令全部留痕，保存 180 天 |
| 费用 | 个人每月上限；超出要说明用途 |
| 项目说明 | 每个仓库一份，由技术负责人维护，每季度复查 |

---

## 6. 指标

| 指标 | 怎么算 | 说明 |
|---|---|---|
| 周活跃使用率 | 每周至少用过一次的工程师比例 | 推广是否成功 |
| Agent 参与的合并比例 | 合并的代码改动中，有 Agent 参与的比例 | 是否真的用在正式工作里 |
| 交付周期 | 从开始做到合并上线的时间 | 效率有没有提升 |
| 缺陷率、回滚率 | 上线后出问题的比例 | **不能上升**，这是质量的底线 |
| 安全事件 | 密钥泄露、越权操作 | **0** |
| 人均月费用 | 总费用除以使用人数 | 和效率提升对比，算投入产出 |

> 产品经理的判断点：**不要用「Agent 写了多少行代码」衡量效果。** 代码行数很容易涨，却不代表价值。看交付周期和缺陷率，一个看快没快，一个看好没好。

---

## 7. 推广路线

| 阶段 | 时间 | 内容 |
|---|---|---|
| 评估 | 第 1 个月 | 三家试用，两周对比，定下一家；和安全团队定好权限和数据条款 |
| 试点 | 第 2 个月 | 两个小组先用；收集问题，补充项目说明和权限规则 |
| 推广 | 第 3 个月 | 全员开通；内部分享最佳用法；每月看指标 |
| 扩展 | 之后 | 评估是否开放云端任务、是否接更多内部系统 |

---

## 8. 面试时怎么讲（一分钟版）

> 我负责的是研发团队引入编程 Agent，目标是三个月内大部分工程师用起来，而且不出安全事故。
>
> 写代码是现成产品最擅长的场景，所以我没有考虑自研，而是直接买成品。我的工作重点放在两件事上：选哪一家，以及怎么配置。
>
> 选型时我按部件列了一张评估表：权限能不能统一下发、能不能挂审计、能不能写团队共享的项目说明、能不能管控外部接入、代码会不会被拿去训练。三家各试用两周，按表打分。
>
> 配置上最重要的是权限三档：读代码、跑测试直接放行；装依赖、删文件要本人确认；读密钥、连生产环境由管理员统一禁止。还有一条：Agent 写的代码照常走测试和代码评审。
>
> 衡量看交付周期和缺陷率，不看代码行数；安全事件的目标是 0。
