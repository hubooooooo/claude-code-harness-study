# 案例：跨境电商售后客服 Agent

知识库助手那个案例，Agent 只读不写。这个案例的不同之处在于：Agent 要**替公司花钱**（退款），还要**直接对客户说话**。权限和规则的分量会重很多。

读的时候可以先遮住每一节的结论，自己判断一遍，再对答案。

---

## 1. 背景

一个做家居小家电的跨境品牌，主要卖给美国和欧洲的客户，用 Shopify 搭的独立站。每天大约 3000 条客服咨询，以英文为主：

| 问题类型 | 占比 | 例子 |
|---|---|---|
| 查物流 | 45% | 「我的包裹到哪了？」 |
| 退换货 | 25% | 「收到的咖啡机漏水，想退货」 |
| 产品使用 | 15% | 「除垢灯一直亮怎么办？」 |
| 其他 | 15% | 改地址、要发票、投诉 |

已知条件：

| 条件 | 情况 |
|---|---|
| 团队 | 4 名工程师，已经在用 OpenAI 的接口做商品描述生成 |
| 客服 | 12 人三班倒，夜间和大促期间严重不够 |
| 数据 | 订单在 Shopify，物流信息在物流商的接口；欧洲客户的数据受 GDPR 约束 |
| 目标 | 夜间和高峰期自动处理大部分咨询，客服人数不增加 |

---

## 2. 先问：真的需要 Agent 吗？

| 问题类型 | 需要几步 | 结论 |
|---|---|---|
| 查物流 | 查订单 → 查物流 → 回复 | 步骤固定，用「快速通道」处理，不进 Agent 循环 |
| 退换货 | 查订单 → 对照退换货政策 → 判断是否符合 → 发起退货或退款 → 告诉客户下一步 | 要看结果决定下一步，需要 Agent |
| 产品使用 | 查说明书 → 回答 → 没解决再换个办法 | 需要多步 |
| 其他 | 不一定 | 先分类，复杂的转人工 |

**结论**：将近一半的咨询（查物流）步骤固定，走快速通道更快更便宜；退换货和产品问题才交给 Agent。

> 产品经理的判断点：同一个产品里可以「部分用 Agent」。先把步骤固定的高频需求分流出去，Agent 只处理真正需要判断的那部分。

---

## 3. 走哪条路？

| 问题 | 这个案例的回答 | 指向 |
|---|---|---|
| ① 真的需要 Agent 吗 | 退换货和产品问题需要 | 继续 |
| ② 内部提效还是做进产品 | 直接面对客户 | 不选成品 |
| ③ 有没有工程师 | 有 4 名，而且有高风险的退款操作 | 低代码平台的权限和钩子偏弱，不适合 |
| ④ 要不要换模型、有没有数据限制 | 客户在海外，团队已经在用 OpenAI；没有换模型的计划 | 可以用厂商开发包 |
| ⑤ Harness 是不是核心竞争力 | 不是 | 不自研 |

**结论：用厂商开发包（这里选 OpenAI Agents SDK）。**

拿选型篇的对照表核对一遍。客服需要的部件是循环、工具、权限、钩子、压缩，再加上「转交给人」。这些它都自带。它缺的是待办、定时、后台任务，而这几项客服用不上。

**缺的部件对你不致命，就可以选。** 这是用部件清单做选型的核心。

两个补充：

- Claude Agent SDK 也能做。它的强项是文件操作、执行代码、跑长任务，客服场景用不上这些，所以选团队已经熟悉的那家。
- 厂商开发包会绑定一家模型。为了以后能换，**退款规则、政策判断这些业务逻辑放在自己的系统里**，不写死在提示词里。换方案时，只需要重新接一遍工具。

---

## 4. 逐个部件：用、暂不用、不用

| 部件 | 决定 | 理由 | 要定的规则 |
|---|---|---|---|
| s01 循环 | **用** | 退换货要多步判断 | 一次咨询最多 8 步；超过就转人工 |
| s02 工具 | **用，6 个** | 查订单、查物流、查政策、建退货申请、退款、转人工 | 改价格、改订单金额的工具一律不给 |
| s03 权限 | **用，这个案例的核心** | Agent 能替公司花钱 | 见下面的三档清单 |
| s04 钩子 | **用** | 每笔退款要可追溯；回复发出前要检查 | 每次退款留痕；回复里不许承诺赔偿金额、不许提竞品；日志里的客户邮箱和地址要脱敏 |
| s05 待办 | 不用 | 单次咨询步骤少 | — |
| s06 子 Agent | 不用 | 没有大量阅读的子任务 | — |
| s07 技能 | **V2 再加** | 不同品类、不同国家的退换货口径不一样 | 由售后主管写和审，政策变了当天更新 |
| s08 压缩 | **用，最简单的** | 投诉类对话可能很长 | 订单号、客户诉求、已经承诺过的事必须原文保留 |
| s09 记忆 | 不用，用订单系统代替 | 客户的历史订单和售后记录 Shopify 里都有 | 需要了解客户时，查系统，不让 Agent 自己记 |
| s10～s13 | 不用 | 用不上 | — |
| s14 MCP | 暂不用 | 只接 Shopify 和物流商两个系统，直接做成内置工具更简单 | 接第三个系统时再评估 |
| s16 工作流 | 不用框架，但把退货流程写死 | 「生成退货单 → 生成退货面单 → 发邮件」每次都一样 | 模型只决定「要不要发起退货」，后面的步骤由程序固定执行 |
| s17 目标判断 | 不用，换成规则 | 「客户满意」没法自动验证 | 结束前问客户问题是否解决；客户点「没解决」就转人工 |

**权限三档清单**：

| 档位 | 操作 |
|---|---|
| **直接放行** | 查订单、查物流、查政策；未发货订单的地址修改（修改前先请客户确认新地址）；50 美元以内、并且符合政策的退款 |
| **先问人（客服主管审批）** | 50～200 美元的退款；超出政策期限但客户坚持的退货 |
| **绝对禁止，Agent 不处理，直接转人工** | 200 美元以上的退款；客户提到受伤、起火、法律诉讼；客户要求删除个人数据（走专门的 GDPR 流程） |

这张表是这个产品最重要的一页纸。金额线不是拍脑袋定的：先拿过去三个月的退款数据算一下，50 美元以内的退款占多少、历史上的误退率是多少，再和财务一起定。

---

## 5. 规则清单

| 类别 | 规则 |
|---|---|
| 能力边界 | 只处理本品牌订单的售前和售后问题 |
| 退款 | 按三档清单执行；同一客户 30 天内自动退款不超过 2 次，超过转人工 |
| 承诺 | 不承诺具体的到货日期、赔偿金额、政策以外的补偿 |
| 安全事件 | 客户提到受伤、起火、冒烟，立即转人工并通知质量负责人 |
| 转人工 | 客户明确要求找真人时，立即转，不挽留 |
| 留痕 | 所有退款、地址修改都记录操作原因和对话原文 |
| 隐私 | 欧洲客户的数据处理符合 GDPR；确认模型厂商的数据处理条款（是否用于训练、保存多久） |

---

## 6. 指标

| 指标 | 怎么算 | 第一期目标 |
|---|---|---|
| 自助解决率 | 没有转人工就结束、客户也没有再来问的比例 | ≥ 50% |
| 首次响应时间 | 客户发消息到收到第一条回复 | 夜间从 6 小时降到 1 分钟以内 |
| 错误退款 | 不该退却退了、金额错误 | **0** |
| 不当承诺 | 抽检发现做了规则以外的承诺 | **0** |
| 客户满意度 | 对话结束后的评分 | 不低于人工客服 |
| 单次成本 | 每次咨询的模型费用 | 低于人工处理成本的十分之一 |

> 产品经理的判断点：「客户满意度不低于人工客服」比「越高越好」更现实。目标是在不降低体验的前提下省人力，不是证明 AI 比人强。

---

## 7. 迭代路线

| 版本 | 内容 | 新增的部件或规则 |
|---|---|---|
| V1 | 查物流快速通道、产品问答；Agent 只读，退换货全部转人工 | 循环、工具（只读）、钩子、压缩 |
| V2 | 开放退换货和小额退款 | 权限三档、写入工具、技能 |
| V3 | 物流延误时主动通知客户 | 定时；无人值守时只能发通知，不能退款 |

先上只读的 V1，跑一个月，拿到真实的对话数据，再决定 V2 的退款金额线定在多少。**写操作永远晚于读操作上线。**

---

## 8. 面试时怎么讲（一分钟版）

> 我做的是一个跨境电商的售后客服 Agent，目标是解决夜间和大促时客服不够的问题。
>
> 我先做了分流：将近一半是查物流，步骤固定，走快速通道；退换货和产品问题才交给 Agent。
>
> 路线上用的是厂商开发包。我拿部件清单核对过：客服要的循环、工具、权限、钩子、转人工它都有，缺的待办、定时客服用不上。为了以后能换方案，退款规则放在我们自己的系统里。
>
> 最核心的是权限三档：50 美元以内、符合政策的退款 Agent 直接做，50 到 200 美元要主管审批，200 以上或者涉及安全问题直接转人工。金额线是拿历史退款数据和财务一起定的。
>
> 上线分两步：先只读跑一个月，再开放退款。核心指标是自助解决率和错误退款次数，错误退款的目标是 0。
