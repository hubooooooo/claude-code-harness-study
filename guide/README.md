# 选型篇：产品经理怎么决定 Agent 用哪些部件

前面 17 章，你把 Agent Harness 拆成了 17 个部件，知道了每个部件是干什么的。这一篇解决下一个问题：**轮到你自己做一个 Agent 产品时，怎么判断该用哪些部件、规则怎么定。**

这是产品经理在面试和工作里最能体现价值的地方。工程师能把部件做出来，但「要不要做、先做哪个、边界在哪里」，需要产品经理来判断和拍板。

这一篇不需要写代码。17 章每章末尾的「产品经理视角」是单个部件的详细判断卡，这一篇把它们放在一起，用来做整体决策。

---

## 先分清三件事

| | 是什么 | 谁来决定 |
|---|---|---|
| **模型** | 负责思考和做决定的「大脑」，比如 Claude、GPT、DeepSeek | 一般是选一家，产品经理参与成本、效果、合规的评估 |
| **Harness** | 让模型能干活的「载具」：循环、工具、权限、记忆……也就是这 17 个部件 | **产品经理决定用哪些部件、规则是什么**；工程师负责实现 |
| **产品** | 用户看到和用到的东西：入口、界面、流程、收费方式 | 产品经理 |

这门课教的是中间那一层。你会发现，很多「Agent 产品做得好不好」的差别，不在模型，而在 Harness 的取舍和规则。

---

## 第一个决策：走哪条路

做一个 Agent 产品，有五条路。用造车打个比方：

| 路线 | 比喻 | 代表 | 上线速度 | 能改多少 | 绑定厂商 | 需要的团队 |
|---|---|---|---|---|---|---|
| **直接用成品** | 买一辆整车 | Claude Code、Codex 这类现成的 Agent 工具 | 最快 | 很少 | 很深 | 几乎不需要工程师 |
| **用厂商开发包** | 买厂商的底盘，自己装车身 | Claude Agent SDK、OpenAI Agents SDK | 快 | 较多 | 深，基本只能用这家的模型 | 少量工程师 |
| **用通用框架** | 买标准零件自己组装 | LangChain、LangGraph | 中等 | 很多 | 浅，可以换模型 | 有经验的工程师 |
| **用低代码平台** | 用乐高拼 | Dify、Coze | 很快 | 有限 | 浅，大多能换模型 | 产品、运营就能上手 |
| **完全自研** | 自己造车 | 这门课的做法 | 最慢 | 全部 | 不绑定 | 资深工程团队 |

这门课走的是最后一条路：照着 Claude Code 的设计思路从零造一遍。目的是让你看懂每个部件，**不是说你的产品就应该自研**。看懂了部件，你才能评估另外四条路：它自带了哪些部件，还缺哪些，缺的那几个对你的产品是不是致命。

### 用五个问题选路线

按顺序问下去，大部分情况都能落到一条路上：

1. **这件事真的需要 Agent 吗？**
   如果步骤完全固定（比如「收到表单 → 校验 → 存档」），或者调用一次模型就能完成，用普通的程序或工作流工具就够了，不需要 Agent。后面「什么时候不该用 Agent」一节有详细清单。
2. **是给自己团队提效，还是做进产品给客户用？**
   给内部提效，而且场景正好是现成工具擅长的（写代码、处理文档），**优先直接用成品**，最省事。
3. **团队有没有工程师？**
   没有，或者只想先验证需求，**用低代码平台**。
4. **要不要换模型？有没有数据或合规限制？**
   - 认定一家模型、数据可以用它的服务：**用这家的开发包**，上线快。不过各家开发包自带的部件差别很大，要对照下面的表。
   - 需要多家模型对比、以后可能换模型，或者必须用国内模型、私有部署：**用通用框架**。绑定海外单一厂商的成品和开发包，在这种情况下基本出局。
5. **Harness 本身是不是你的核心竞争力？**
   只有当 Agent 的运行方式本身就是你和对手拉开差距的地方，或者部署环境特殊到现成方案都不支持时，才值得**完全自研**。

> 选型不是一锤子买卖。常见做法是先用最快的路线验证需求，验证通过后再换成更可控的方案。面试时讲清楚「为什么分阶段、什么条件下切换」，比只报一个框架名字有说服力得多。

光看部件还不够，还要看许可证和限制。下面这些往往直接决定能不能选：

| 方案 | 许可证 | 模型 | 选型前一定要知道的限制 |
|---|---|---|---|
| Claude Agent SDK | 代码是 MIT，但**使用受 Anthropic 商业条款约束** | 只能用 Claude（可通过 Anthropic、AWS、Google 等渠道调用） | 自带的部件最多，几乎就是 Claude Code 的全套能力；产品不能叫「Claude Code」；给第三方用户的产品必须用 API Key |
| OpenAI Agents SDK | MIT | 默认 OpenAI，可以接其他模型（测试中） | 轻量，待办、定时、后台任务都要自己做；部分能力只有 OpenAI 模型能用 |
| LangGraph / LangChain | MIT | 不绑定 | 部件很全，但要工程师自己拼装；定时任务和托管运行属于收费的 LangSmith 平台 |
| Dify | **修改版 Apache 2.0**：未经书面授权，不能用它的源码做多租户服务，也不能去掉界面上的标识 | 不绑定 | 适合企业内部自己部署；新版 Agent 还在测试；权限和钩子弱 |
| Coze 开源版 | Apache 2.0 | 不绑定 | 只有单 Agent；MCP 调用尚未实现 |

从这两张表能读出几条判断：

- **想最快拿到完整能力、也认可只用 Claude**：Claude Agent SDK 自带的部件最多，代价是绑定一家模型和它的商业条款。
- **要换模型、流程复杂、要求可控**：LangGraph 部件齐全，但需要有经验的工程师。
- **没有工程师、先验证需求**：低代码平台最快，但权限、钩子这两项偏弱。产品里只要有高风险的「写」操作（退款、删数据、对外发消息），就要认真评估它够不够用。
- **准备把 Agent 做成服务卖给多家客户**：先看许可证。Dify 的许可证不允许未经授权做多租户服务。
- **持久任务板（s10）和团队协作（s13）几乎没有一家现成提供**：产品要是离不开这两项，就意味着不小的自研工作量。

这也正是学 17 个部件的意义：有了这张清单，评估任何新出的框架，都能在十分钟内看出它缺什么。

## 第二个决策：启用哪些部件

### 原则：最小可行 Harness

**从最少的部件开始，出现了明确的症状再加。** 每多一个部件，就多一份成本、多一种出错的可能、多一点排查难度。

按「必要程度」，17 个部件大致分三档：

| 档位 | 部件 | 说明 |
|---|---|---|
| **几乎都要** | s01 循环、s02 工具 | 没有它们就不是 Agent |
| **几乎都要，只要有「写」操作** | s03 权限 | 只要 Agent 能改数据、发消息、花钱，就必须有 |
| **按症状加** | s04 钩子、s05 待办、s07 技能、s08 压缩、s09 记忆、s14 MCP | 出现对应症状时再加，大多数产品会用到其中几个 |
| **谨慎上** | s06 子 Agent、s10 任务板、s11 后台任务、s12 定时、s16 工作流、s17 目标判断 | 解决特定问题，代价明显，要有充分理由 |
| **最后才考虑** | s13 团队 | 成本和复杂度最高，绝大多数产品用不上 |

（s15 是把前面部件组合在一起，不是单独的部件。）

### 判断每个部件的五个问题

对每个部件，都可以问这五个问题：

1. **信号**：出现什么症状，说明你需要它？
2. **代价**：加上它要付出什么？成本、速度、新的出错方式、排查难度。
3. **替代**：不加它，有没有更便宜的办法？
4. **规则**：真要用，你要拍板哪些规则？
5. **衡量**：怎么知道它起作用了？

前四个问题的答案，汇总在下面的判断卡里。第五个问题见后面的「指标清单」。

### 部件判断卡

| 部件 | 什么信号说明需要它 | 代价 | 先试试更便宜的办法 | 你要拍板的规则 |
|---|---|---|---|---|
| **s01 循环** | 任务要多步，而且要看上一步的结果才能决定下一步 | 步数不可控，成本和耗时不确定 | 单次调用模型，或者固定流程 | 最多走几步；单个任务的费用和时间上限；超限后停下问人还是直接结束 |
| **s02 工具** | 需要查数据、改系统、动手操作 | 工具越多，模型越容易选错；每个工具都要写清楚说明 | 把需要的资料直接写进提示词 | 给哪些工具（越少越好）；哪些只读、哪些能写；工具说明由谁写、谁审 |
| **s03 权限** | 有不可撤销、花钱、对外的操作：删数据、发邮件、付款、对客户说话 | 每次确认都打断用户；确认太多，用户会不看就点同意 | 只给只读工具；在隔离环境里运行 | 三档清单：直接放行 / 先问人 / 绝对禁止；谁有权批准；被拒后怎么告诉用户 |
| **s04 钩子** | 要统一加审计日志、合规检查、敏感词过滤、计费，不想每个工具各写一遍 | 钩子多了，流程不透明，也会变慢 | 在单个工具里直接写死 | 哪些时机必须留痕；哪些检查有权否决执行 |
| **s05 待办** | 任务超过五到十步；用户反馈「做着做着忘了」「漏了几项」 | 每轮多一次更新，多占上下文 | 让用户自己拆任务 | 多复杂的任务必须先列计划；计划要不要给用户先确认 |
| **s06 子 Agent** | 某个子任务要读大量资料，但最后只需要一个结论；主对话因此被挤满 | 多一轮模型调用；子 Agent 看不到主对话，任务说明写不清就跑偏；排查链路变长 | 上下文够用就单个 Agent 做完；或者先压缩（s08） | 哪类任务允许派出去；子 Agent 能用哪些工具（通常只读）；最多派几个；结果必须按什么格式交回 |
| **s07 技能** | 有好几套专门的操作规范（报销流程、合同审查口径），全塞进提示词太长、互相干扰 | 模型可能想不起来加载；技能要有人维护 | 只有一两套规范，直接写进提示词 | 技能由谁写、谁审、多久更新；目录里的描述怎么写才能被正确用上 |
| **s08 压缩** | 对话或任务一长，模型开始忘掉前面的内容，成本飙升，甚至报错超长 | 压缩会丢细节，可能丢掉关键信息 | 开一个新会话；限制单个任务的长度 | 什么必须原文保留（用户的要求、金额、承诺）；多长开始压缩；完整记录要不要存档 |
| **s09 记忆** | 用户反复交代同样的偏好和背景；需要跨天延续 | 隐私合规风险；记错比不记更糟；要给用户查看和删除的入口 | 让用户自己填「个人设置」 | 记什么、不记什么（敏感信息禁止）；保存多久；用户能否查看和删除；新旧记忆冲突以谁为准 |
| **s10 任务板** | 一个目标要拆成多个有先后顺序的任务，要跨会话、跨人持续推进，还要能看进度 | 要维护任务状态，处理卡住的任务 | 待办清单（s05）够用就不要上 | 任务拆多细；谁能建、认领、关闭；卡住多久升级给人 |
| **s11 后台任务** | 有慢操作（跑报表、长查询、批量处理），用户只能干等 | 结果回来的时机不好控制；失败了要有人知道 | 让用户等；或者把任务拆小 | 多慢算慢（超过多久转后台）；完成后怎么通知；失败谁兜底 |
| **s12 定时** | 要按时间主动做事：日报、巡检、提醒 | 没人盯着时出错没人发现；定时任务越积越多 | 用系统自带的定时器，每次调用一次模型，不需要 Agent 循环 | 谁能设定时任务；频率上限；到期是否自动停止；无人值守时允许做哪些事（通常要更严） |
| **s13 团队** | 任务大到一个 Agent 处理不完，而且能拆成边界清楚、可以同时做的几块 | 成本成倍增加；协调出错、结果冲突；最难排查 | 子 Agent（s06）或工作流（s16） | 最多几个队友；各自的权限边界；结果冲突谁裁决；总预算 |
| **s14 MCP** | 要接已有系统（CRM、工单、知识库）或第三方能力，希望用通用的接口 | 第三方服务的安全和稳定性风险；工具一多，模型更难选对 | 只接一两个系统时，直接做成内置工具 | 允许接哪些服务（白名单）；外部工具默认按什么权限处理；数据能不能流出公司 |
| **s16 工作流** | 流程固定，要求每次步骤一致、可以审计、中断后能接着跑（审核流程、批量处理） | 不够灵活，遇到意外不会变通；流程一变就要改脚本 | 让模型自己规划（s05） | 哪些步骤必须固定、哪些交给模型；失败后重跑的策略 |
| **s17 目标判断** | 完成标准可以客观验证（测试通过、字段齐全、格式合规），而模型经常「自称做完了」 | 多一次模型调用；标准写不清会被反复打回 | 让用户自己验收；用普通程序检查格式 | 完成标准怎么写；最多打回几次；一直达不到时怎么交给人 |

## 什么时候不该用 Agent

下面这些情况，Agent 往往不是最好的选择：

| 情况 | 为什么 | 更合适的做法 |
|---|---|---|
| 流程完全固定 | Agent 的价值在于「看情况决定下一步」，流程固定时这个能力用不上，反而带来不确定性 | 普通程序、工作流引擎、RPA |
| 调用一次模型就能完成 | 循环、工具都是多余的成本 | 直接调用模型，比如做摘要、翻译、分类 |
| 要求毫秒级响应 | Agent 要多次调用模型，天然慢 | 规则引擎、传统算法 |
| 错一次代价极高，又没法让人审核 | 模型总有出错的概率 | 人来做，Agent 只做辅助建议 |
| 对每单成本极度敏感 | 多步调用的成本难以预估 | 先算清楚每次任务的成本上限，再决定 |

能说出「这个场景我不建议用 Agent」，往往比能说出怎么用更能体现判断力。

## 第三个决策：把规则写下来

判断做完，要落成一页纸，交给工程、法务、安全一起评审。可以按这个模板写：

**Harness 设计说明（一页纸）**

1. **目标与边界**：这个 Agent 要解决什么问题；明确不做什么。
2. **路线选择**：走哪条路，为什么；什么条件下会换路线。
3. **启用的部件**：每个部件为什么要用（对应的症状）。
4. **暂不启用的部件**：为什么不用；什么症状出现时再加。
5. **规则清单**：
   - 权限三档：直接放行 / 先问人 / 绝对禁止
   - 步数、费用、时间上限
   - 记忆政策：记什么、存多久、用户怎么删
   - 人工介入点：什么情况交给人
6. **指标与目标值**：见下方清单。
7. **风险与兜底**：最坏会发生什么，发生了怎么办。

## 指标清单

判断一个部件有没有起作用，要看数据。常用指标：

| 指标 | 说明 | 主要反映哪些部件 |
|---|---|---|
| 任务完成率 | 用户的任务最终被完成的比例 | 整体 |
| 一次成功率 | 不用返工、不用人工补救就完成的比例 | s05 待办、s17 目标判断 |
| 人工介入率 | 需要人接手的比例 | s03 权限、s17 目标判断 |
| 平均步数、平均耗时 | 完成一个任务要几步、多久 | s01 循环、s06 子 Agent |
| 单个任务成本 | 平均每个任务花多少模型费用 | s06、s08、s13 |
| 越权、误操作次数 | 做了不该做的事 | s03 权限、s04 钩子；目标通常是 0 |
| 采纳率、满意度 | 用户愿不愿意继续用 | 整体 |

## 面试怎么讲

### 答题框架：场景 → 症状 → 部件 → 代价 → 规则 → 指标

不管被问到哪个部件，都可以按这个顺序回答：**在什么场景下，出现了什么症状，所以用了什么部件，付出了什么代价，定了哪些规则，用什么指标证明有效。**

### 三道常见题

**题 1：「让你做一个客服 Agent，你会怎么设计？」**

答题要点：

- 先问清楚：客服要处理哪些问题？哪些操作是只读的（查订单），哪些会改变外部世界（退款、改地址）？
- 路线：要接订单系统、退款系统，客户数据敏感，一般用通用框架或厂商开发包，不会用成品工具。
- 部件：循环、工具、权限一定要；退款、改地址放进「先问人」那一档，或者设金额上限；接已有系统用 MCP；对话长了要压缩。
- 规则：退款金额上限；禁止承诺系统做不到的事；客户情绪激动时转人工。
- 指标：自助解决率、转人工率、退款误操作次数（目标为 0）、客户满意度。

**题 2：「Agent 把用户的数据删了，作为产品经理你会怎么避免？」**

答题要点：

- 这是权限（s03）的问题，不是模型的问题。模型总有概率出错，要靠 Harness 兜底。
- 删除这类不可撤销的操作，放进「先问人」或「绝对禁止」那一档。
- 能用「软删除」（先进回收站）就不用真删。
- 用钩子（s04）记录每一次删除，做到可追溯。
- 进一步：只在隔离环境里执行，或者只给只读工具。

**题 3：「为什么不直接用 Dify / LangChain，要自己搭？」**

答题要点：

- 不存在绝对正确的选择，要看五个问题：要不要 Agent、内部还是对外、有没有工程师、模型和数据限制、Harness 是不是核心竞争力。
- 拿 17 个部件做清单逐项对照：现成方案自带哪些、缺哪些，缺的那几个对产品是不是致命。
- 给出阶段性方案：比如先用低代码平台验证需求，再换成通用框架做深度集成。

## 完整案例

四个案例走的是四条不同的路，都按同一套方法推导：要不要 Agent → 走哪条路 → 逐个部件定用不用 → 规则 → 指标 → 迭代。

| 案例 | 走的路 | 看点 |
|---|---|---|
| [企业内部知识库助手](case-knowledge-base.md) | 先低代码平台验证，再换通用框架 | 只读 Agent；数据权限是核心 |
| [跨境电商售后客服](case-customer-service.md) | 厂商开发包 | Agent 要替公司退款；权限三档按金额划线 |
| [研发团队引入编程 Agent](case-coding-agent.md) | 直接买成品 | 买了成品，产品经理要定的是配置 |
| [竞品和舆情日报](case-daily-report.md) | 低代码平台的工作流 | 大部分环节不该用 Agent |
