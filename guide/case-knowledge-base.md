# 案例：企业内部知识库助手

这个案例把「选型篇」的方法完整走一遍：从需求出发，先判断要不要 Agent，再决定走哪条路，然后逐个部件决定用不用、规则怎么定，最后定指标和迭代路线。

读的时候可以先遮住每一节的结论，自己判断一遍，再对答案。

---

## 1. 背景

一家 2000 人的公司，员工每天在群里问大量重复问题：

- 「年假怎么算？今年还剩几天？」
- 「报销发票抬头写什么？」
- 「VPN 连不上怎么办？」
- 「新员工入职要走哪些流程？」

答案其实都在文档里，但文档散落在飞书知识库、共享盘和几个老系统里，版本还经常对不上。HR 和 IT 每人每天要花 1～2 小时重复回答。

老板的要求：**做一个员工随时能问的助手，让 HR 和 IT 少回答重复问题。**

已知条件：

| 条件 | 情况 |
|---|---|
| 团队 | IT 部门有 2 名工程师，可以兼职投入；没有专职 AI 团队 |
| 数据 | 制度文档、员工信息都在公司内网，属于敏感信息 |
| 入口 | 员工都用飞书，希望直接在飞书里问 |
| 时间 | 老板希望一个月内看到效果 |

---

## 2. 先问：真的需要 Agent 吗？

把员工的问题分一下类：

| 问题类型 | 例子 | 需要几步 | 结论 |
|---|---|---|---|
| 查一条规定 | 「报销发票抬头写什么」 | 搜一次文档，回答 | 不需要 Agent，「检索 + 一次回答」就够 |
| 要结合个人信息 | 「我今年还剩几天年假」 | 查制度 + 查本人数据 + 计算 | 需要多步，适合 Agent |
| 要排查 | 「VPN 连不上」 | 问症状 → 查手册 → 给方案 → 不行再换方案 | 需要多步、看结果决定下一步，适合 Agent |
| 要比对 | 「新旧差旅标准有什么区别」 | 找两份文档、对比 | 需要多步 |

**结论**：大约六成问题用最简单的「检索 + 回答」就能解决，但剩下的问题需要多步查询和判断。所以做一个**轻量的 Agent**：有循环、能查多处资料，但步数和权限都收得很紧。

> 产品经理的判断点：不要因为「Agent 很火」就上 Agent。先看有多少比例的需求真的需要「看结果再决定下一步」。

---

## 3. 走哪条路？

按选型篇的五个问题逐个过：

| 问题 | 这个案例的回答 | 指向 |
|---|---|---|
| ① 真的需要 Agent 吗 | 需要轻量 Agent | 继续 |
| ② 内部提效还是做进产品 | 内部提效，但要接飞书、按员工权限查数据，不是现成产品能直接满足的 | 不选「直接用成品」 |
| ③ 有没有工程师 | 只有 2 名兼职工程师 | 低代码平台做验证最快 |
| ④ 要不要换模型、有没有数据限制 | 员工信息敏感、在内网，公司倾向国内模型或私有部署 | 绑定海外单一厂商的方案风险高 |
| ⑤ Harness 是不是核心竞争力 | 不是，助手只是内部工具 | 不值得完全自研 |

**结论：分两步走。**

1. **第 1 个月：用低代码平台（如 Dify）做验证版。** 先接一部分制度文档，在一个部门试用，验证「员工真的会用、答案靠谱」。
2. **验证通过后：换成通用框架（如 LangGraph）做正式版。** 原因是正式版要做「按员工权限过滤文档」「查个人年假数据」「接工单系统」这些深度集成，低代码平台很难做细；而通用框架不绑定模型，能接公司选定的国内模型。

> 产品经理的判断点：选型不是一锤子买卖。用最快的方式先验证需求，再为正式版换更可控的方案。面试时把「为什么分两步、什么条件下切换」讲清楚，比只报一个框架名字有说服力得多。

## 4. 逐个部件：用、暂不用、不用

用选型篇的「五问」逐个判断。下面是正式版第一期（V1）的结论：

| 部件 | 决定 | 理由 | 要定的规则 |
|---|---|---|---|
| s01 循环 | **用** | 排查类、个人类问题要多步 | 一次提问最多 6 步；超过就停下，建议转人工 |
| s02 工具 | **用，只给 4 个只读工具** | 搜知识库、读文档全文、查本人假期余额、查 IT 故障手册 | 不给任何「写入」工具；每个工具的说明由对应部门审核 |
| s03 权限 | **用，重点是数据权限** | 工具虽然只读，但**员工只能查到自己有权看的文档和自己的数据** | 搜索结果按员工的飞书部门和职级过滤；绝对禁止查询他人薪酬、绩效 |
| s04 钩子 | **用** | 需要统一做审计日志和敏感词检查 | 每次提问、每次工具调用都留痕，保留 180 天；回答里出现身份证号、薪资数字时拦截 |
| s05 待办 | 不用 | 单次问答步数少，用不上计划清单 | — |
| s06 子 Agent | 暂不用 | 目前没有「读大量资料只要一个结论」的子任务 | 等出现「对比十几份文档」的需求再评估 |
| s07 技能 | **V2 再加** | HR 政策解读、IT 排障各有一套口径，以后可以做成两份技能说明 | 技能内容由 HR、IT 负责人写和审核，每季度更新 |
| s08 压缩 | **用，最简单的一层** | 排查类对话可能来回十几轮 | 只保留最近几轮工具结果全文；用户给出的设备型号、报错信息必须原文保留 |
| s09 记忆 | 暂不用 | 记住员工的部门、常用系统会更方便，但涉及隐私 | V2 前先过隐私评审；只记「工作相关偏好」，员工可查看、可删除 |
| s10 任务板 | 不用 | 不涉及长期多步任务 | — |
| s11 后台任务 | 不用 | 没有慢操作 | — |
| s12 定时 | **V3 再考虑** | 每周主动推送「制度更新摘要」是个好功能 | 只推送公开制度；员工可退订 |
| s13 团队 | 不用 | 完全没有必要，成本和复杂度都太高 | — |
| s14 MCP | **用** | 通过 MCP 接飞书知识库、假期系统，以后换系统时少改动 | 只允许接入 IT 审核过的服务；所有外部工具一律按只读处理 |
| s16 工作流 | 不用 | 问答不是固定流程 | — |
| s17 目标判断 | 不用，换成一条更便宜的规则 | 问答没有可以自动验证的「完成标准」 | 改成：**回答必须附出处链接；找不到依据就明确说不知道，并给出 HR、IT 的人工联系方式** |

**数一下**：V1 只用了 6 个部件（s01、s02、s03、s04、s08、s14），外加一条代替 s17 的规则。这正是「最小可行 Harness」的思路：先用最少的部件解决核心问题，症状出现了再加。

## 5. 规则清单（交给开发和法务的那一页）

| 类别 | 规则 |
|---|---|
| 能力边界 | 只回答公司制度、流程、IT 使用问题；其他问题礼貌拒绝 |
| 数据权限 | 按员工身份过滤文档；本人数据只能查本人；他人薪酬、绩效一律不可查 |
| 回答质量 | 必须附出处；没有依据不编造，直接说不知道并给人工渠道 |
| 步数和成本 | 每次提问最多 6 步；单次成本超过预设上限时停止 |
| 留痕 | 提问、工具调用、回答全部记录，保留 180 天，仅安全部门可查 |
| 敏感信息 | 回答中出现身份证号、薪资等敏感信息时拦截 |
| 人工兜底 | 连续两次回答被员工标记「没用」时，自动推荐转人工 |

## 6. 用什么指标判断做得好不好

| 指标 | 怎么算 | 第一期目标 |
|---|---|---|
| 自助解决率 | 员工问完没有再找人工的比例 | ≥ 60% |
| 转人工率 | 被推荐或主动转人工的比例 | ≤ 25% |
| 答案准确率 | 每周抽检 50 条，人工判断是否正确 | ≥ 90% |
| 引用正确率 | 回答附的出处确实支持回答内容 | ≥ 95% |
| 越权次数 | 查到不该查的数据 | **0**（出现一次就是事故） |
| 单次成本 | 平均每次提问的模型费用 | 控制在预算内 |
| HR / IT 节省时间 | 重复答疑时间的减少 | 每人每天减少 1 小时 |

> 产品经理的判断点：「越权次数」这类指标的目标只能是 0。它决定了 s03 权限为什么是这个案例里最重要的部件。

## 7. 迭代路线

| 版本 | 时间 | 内容 | 新增部件 |
|---|---|---|---|
| 验证版 | 第 1 个月 | 低代码平台，接一部分制度文档，一个部门试用 | 循环、工具 |
| V1 | 第 2～3 个月 | 换通用框架；按员工权限过滤；接假期系统；全公司上线 | 权限、钩子、压缩、MCP |
| V2 | 第 4～6 个月 | 把 HR、IT 口径做成技能；隐私评审后加记忆 | 技能、记忆 |
| V3 | 之后 | 每周推送制度更新；能帮员工直接提 IT 工单（第一次出现写入操作，要重新评估权限） | 定时；权限规则升级 |

注意 V3 的「帮员工提工单」：这是第一次出现**写入操作**，权限规则要从「只读」升级为「提交前先让员工确认」。每当产品要做「会改变外部世界」的事，都要重新过一遍权限。

---

## 8. 面试时怎么讲这个案例（一分钟版）

> 我做的是一个企业内部知识库助手，目标是减少 HR 和 IT 的重复答疑。
>
> 我先判断了要不要 Agent：六成问题检索一次就能答，但查个人数据、排查故障这类问题需要多步，所以做了一个步数受限的轻量 Agent。
>
> 路线上分两步：先用低代码平台一个月验证需求，验证通过后换成通用框架，因为要按员工权限过滤数据、接内部系统，而且公司要求用国内模型。
>
> 部件上只用了 6 个，最重要的是权限：工具全部只读，按员工身份过滤文档，越权指标的目标是 0。我没有用目标判断器，换成了一条更便宜的规则：必须附出处，找不到就说不知道并给人工渠道。
>
> 上线后看自助解决率、准确率和越权次数，第一期目标是自助解决率 60% 以上。
