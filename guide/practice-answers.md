# 练习参考答案与评分要点

> **先做题，再看答案。** 先把 [练习](practice.md) 里的结论卡填完，再来对照。

这里的答案是「参考」，不是唯一解。评分看三样：路线有没有对应到具体条件，部件有没有对应到具体症状，规则能不能落地。路线选得和参考答案不一样，但理由站得住，也可以给分。每题后面都写了哪些答案可以接受。

部件支持情况以选型篇「各条路线自带哪些部件」一表为准（2026 年 10 月核对）。正式选型前要按当时的官方文档再核对一遍。

| 题 | 参考路线 |
|---|---|
| 第 1 题 销售查询助手 | ④ 低代码平台 |
| 第 2 题 SaaS 报表助手 | ② 厂商开发包 |
| 第 3 题 商品文案 | 不用 Agent |
| 第 4 题 合同审查系统 | ③ 通用框架 |
| 第 5 题 行政财务提效 | ① 直接用成品 |
| 第 6 题 编程 Agent 创业公司 | ⑤ 完全自研 |
| 第 7 题 夜间运维值班（验收） | ③ 通用框架 |

## 第 1 题：销售团队的查询助手 → ④ 低代码平台

### 参考结论卡

**1. 要不要 Agent：部分环节要。**
- 查参数：搜一次文档就能回答，「检索 + 一次回答」就够。
- 查客户订单和跟进记录、算报价：要先查 CRM，再查报价规则，再计算，下一步取决于上一步的结果，适合 Agent。

**2. 路线：④ 低代码平台（如 Dify、Coze 开源版，部署在公司内网）。**
- 没有工程师，有一位会用 Dify 的运营；两周内要上线，属于先验证需求。对应五个问题的第 3 条。
- 排除 ① 成品：要接自家 CRM 和产品文档，在飞书里用，这不是现成工具擅长的通用场景。
- 排除 ②③⑤：都需要工程师，两周也来不及。
- 许可证：在公司内部自己部署、自己用，不涉及 Dify 许可证限制的多租户服务。

**3. 部件（对照低代码平台）**

| 部件 | 平台情况 | 判断 |
|---|---|---|
| s01 循环、s02 工具 | 自带 | 用 |
| s14 MCP / 工具接入 | Dify 支持 | 用它接 CRM 和文档 |
| s03 权限 | 弱，只能在流程里加人工节点 | 只读场景够用，但**数据权限不能靠它**，见规则 |
| s08 压缩 | 只截断不摘要 | 问答都很短，不致命 |
| s09 记忆 | Dify 没有 | 不需要 |
| 其他部件 | — | 用不上 |

缺的部件都不致命，低代码平台够用。

**4. 关键规则**
- 查 CRM 时必须带上提问人的身份，由 CRM 接口按人过滤：销售只能查自己负责的客户。**不能靠提示词说「不要告诉他别人的客户」。**
- 只读：不开放任何修改 CRM 的接口。
- 报价只给「规则测算的参考价」，标明以内勤确认为准。

**5. 指标**：销售问内勤的次数下降比例；回答准确率（每周抽检）；越权查到他人客户的次数，目标 0。

**6. 换路线的条件**：要让 AI 写回 CRM（比如自动记跟进记录），或数据权限规则复杂到平台做不了，就换 ③ 通用框架。

### 评分要点
- **必须答到**：没有工程师加两周上线，所以选低代码；数据权限要在 CRM 接口层按人过滤。
- **常见错误**：认为「只读就不用管权限」；直接选成品，忽略了要接自家系统。
- **也可接受**：选 ① 成品的企业版、接 CRM 连接器。前提是说清楚成品能接上这家公司的 CRM，并且能按人过滤数据。

## 第 2 题：SaaS 产品里的数据报表助手 → ② 厂商开发包

### 参考结论卡

**1. 要不要 Agent：要。** 「查数据 → 看结果 → 决定怎么画图 → 生成报告 → 发邮件」，每一步取决于上一步。

**2. 路线：② 用已签约厂商的开发包。** 如果厂商是 Anthropic，就用 Claude Agent SDK；如果是 OpenAI，就用 OpenAI Agents SDK。
- 认定一家模型，数据可以用它的服务，两个月要上线。对应五个问题的第 4 条。
- 排除 ① 成品：这是做进产品卖给客户，不是内部提效。
- 排除 ④ 低代码：权限和钩子弱，而这里有多租户数据隔离和对外发邮件。
- 排除 ⑤ 自研：Harness 不是这家公司的核心竞争力，两个月也来不及。
- **还要查条款**：比如 Claude Agent SDK 的使用受 Anthropic 商业条款约束，给第三方用户的产品必须用 API Key，产品也不能叫「Claude Code」。

**3. 部件（对照开发包）**

两家开发包自带的部件差别很大，这是本题的考点：

| 部件 | Claude Agent SDK | OpenAI Agents SDK | 判断 |
|---|---|---|---|
| s01 循环、s02 工具 | ✅ | ✅ | 用：查数据、画图、生成报告、发邮件 |
| s03 权限 | ✅ | ✅ | 用：发邮件先问 |
| s04 钩子 | ✅ | ✅ | 用：每次查询留痕、计费 |
| s07 技能 | ✅ | ◐ | 用：把报表口径（退货率怎么算）写成技能 |
| s08 压缩 | ✅ | ◐ | 用：长对话需要 |
| s11 后台任务 | ✅ | ✗ 要自己做 | 用：大查询要跑几分钟，转后台，完成后通知 |
| s09 记忆 | ✅ | ◐ | 暂不用：客户多次提出同样的偏好时再加 |
| s12 定时 | ◐ | ✗ | 暂不用：客户要求「每周自动发报表」时再加 |
| s06、s10、s13、s16、s17 | — | — | 不用 |

**4. 关键规则**
- 多租户隔离：查询工具只能拿到当前客户店铺的数据，由数据库账号和接口保证，不靠模型自觉。
- 查询用只读账号；发邮件只能发到客户自己账号绑定的邮箱，其他地址先问。
- 单次提问的费用和时间上限，超过一定时长的查询转后台。

**5. 指标**：回答准确率；越权查到其他客户数据的次数，目标 0；单次提问平均成本；客户使用率和复用率。

**6. 换路线的条件**：业务要进入必须用其他模型的市场，或要同时对比多家模型时，换 ③ 通用框架。

### 评分要点
- **必须答到**：做进产品卖给客户，所以排除成品；认定一家模型，所以选开发包；多租户数据隔离。
- **加分**：指出两家开发包自带部件不同，选 OpenAI 那家就要自己做后台任务；提到厂商条款。
- **常见错误**：只写「用 SDK」，不对照它缺什么；忽略「发邮件」是对外操作。
- **也可接受**：选 ③ 通用框架，前提是理由是「将来大概率要换模型」，并说明上线时间会变长。

## 第 3 题：商品详情页文案批量生成 → 不用 Agent

### 参考结论卡

**1. 要不要 Agent：不要。**
- 每个商品的步骤完全一样：读一行参数 → 按模板生成文案 → 检查违禁词 → 输出。下一步做什么，不取决于上一步的结果。
- 对应选型篇「什么时候不该用 Agent」里的两条：流程完全固定；调用一次模型就能完成。

**2. 怎么做（代替方案）**
- 每个商品**调用一次模型**：提示词里放好统一的风格要求和两三段范文。
- 违禁词检查**用普通程序**：准备一张违禁词表，逐条匹配。比让模型自查可靠，而且不花钱。
- 不合格的自动重写一次，还不合格的交给人改；运营每批抽检一部分。
- 工具：低代码平台的工作流批量处理，或表格软件自带的 AI 功能都可以，不需要工程师。

**3. 部件**：不涉及。如果硬要对照，只用到「调用模型」这一步，没有循环，也没有工具。

**4. 关键规则**：违禁词表由谁维护；抽检比例；上传前必须有人过目。

**5. 指标**：每个商品的平均成本和耗时；违禁词漏检数，目标 0；运营改稿率。

**6. 什么时候才需要 Agent**：比如要 AI 自己去竞品页面调研卖点，再决定怎么写，步骤开始取决于中间结果了，才值得考虑。

### 评分要点
- **必须答到**：明确说「不需要 Agent」，并给出代替方案；违禁词用程序检查。
- **加分**：给出向老板解释的说法。比如：「用 Agent 每个商品要多花几倍的钱和时间，效果不会更好；用固定流程更便宜、更稳定，出了问题也好查。」
- **常见错误**：老板说做 Agent 就做 Agent，开始挑部件。

## 第 4 题：律所的合同审查系统 → ③ 通用框架

### 参考结论卡

**1. 要不要 Agent：要。** 审查时要先识别合同类型，再按对应口径逐条查，查到疑点还要回头翻附件核对，步骤取决于中间发现。

**2. 路线：③ 通用框架（如 LangGraph），接国内模型或私有部署的模型。**
- 数据不能出境，要多家模型对比、以后可能换模型。对应五个问题的第 4 条。
- 排除 ① 成品、② 开发包：绑定海外单一厂商，数据出境，这里基本出局。
- 排除 ④ 低代码：**要卖给其他律所，属于多租户服务，Dify 的许可证未经书面授权不允许**；权限和钩子也偏弱。
- 排除 ⑤ 自研：核心竞争力是审查口径和法律知识，不是 Harness 本身；外包团队只有 4 人，框架的部件已经够用。

**3. 部件（框架基本都有，产品经理决定启用哪些）**

| 部件 | 判断 | 对应症状 |
|---|---|---|
| s01 循环、s02 工具 | 启用 | 读合同、查条款库和法规库 |
| s07 技能 | **启用，关键** | 四类合同的审查口径不同，各写一份技能，由资深律师维护 |
| s06 子 Agent | **启用** | 几十页的合同按章节分给子 Agent 审，只带回风险点。比压缩更稳 |
| s08 压缩 | 谨慎 | 压缩会丢细节，法律文本里一个词就能改变意思。能分段就不压缩 |
| s17 目标判断 | **启用，关键** | 「每个必查条款都有结论」可以客观核对，没查完就打回。LangGraph 里这项还是测试版，可能要自己补一部分 |
| s16 工作流 | 启用 | 审查流程固定：分段 → 逐段审 → 汇总 → 核对清单 → 交律师，适合写成工作流，中断能续跑 |
| s03 权限 | 启用 | 只出审查意见，不能改合同原文，不能发给客户 |
| s04 钩子 | 启用 | 留痕：哪份合同、AI 标了什么、律师改了什么 |
| s11 后台任务 | 可选 | 长合同审查转后台，完成后通知律师 |
| s14 MCP | 可选 | 接律所的文档管理系统 |
| s09 记忆 | 不用 | 保密要求：不能跨客户记住合同内容 |
| s10、s12、s13 | 不用 | 没有对应症状 |

**4. 关键规则**
- 每家律所的数据完全隔离，不出境，不用于训练模型。
- AI 只出意见，最终结论由律师签字，界面上要标明「AI 初审」。
- 必查条款清单由律师维护，清单没有全部覆盖，就不能交给律师。

**5. 指标**：必查条款覆盖率，目标 100%；漏报率（律师复核时发现 AI 漏掉的风险点）；律师审一份合同节省的时间；数据出境次数，目标 0。

**6. 换路线的条件**：如果放弃对外销售，只在本所内部使用，可以考虑 ④ 低代码平台私有部署，先快速验证。

### 评分要点
- **必须答到**：数据不能出境、要换模型，所以排除成品和开发包；多租户许可证问题；技能管审查口径；必查条款要能客观核对。
- **加分**：指出长合同用子 Agent 分段比压缩更稳；用工作流固定审查流程。
- **常见错误**：选 Dify 但没注意「卖给其他律所」带来的许可证问题；记忆部件全开，忽略保密。

## 第 5 题：行政财务团队的日常提效 → ① 直接用成品

### 参考结论卡

**1. 要不要 Agent：要。** 对账、汇总邮件这类活要多步操作，而且要看中间结果。但不用自己做，买现成的就行。

**2. 路线：① 直接用成品，即现成办公类 Agent 产品的企业版。**
- 给内部提效，场景是现成工具擅长的通用办公。对应五个问题的第 2 条。
- 没有工程师，下周就要用，买成品最快。
- 排除 ②③⑤：都需要工程师。
- 排除 ④ 低代码：通用办公场景没有必要自己搭，成品的能力更全。

**3. 部件：成品已经自带，产品经理要定的是配置。** 部件从「要不要做」变成了「怎么配」，这是本题的考点。

| 部件 | 变成了什么配置 |
|---|---|
| s03 权限 | 删除文件、发送邮件之前必须确认；工资表等敏感目录不允许访问 |
| s14 连接器 | 只接企业邮箱和网盘；财务系统先不接，或只读 |
| s09 记忆 | 是否开启；员工能否查看和删除 |
| s04 审计 | 管理后台能不能看到操作日志。这一条本身就是挑选产品的标准 |

选产品时要核对：企业协议里是否承诺数据不用于训练；有没有管理后台和审计日志；能不能按部门配置权限。

**4. 关键规则**
- AI 不得直接付款、提交报销审批。
- 对外发出的邮件必须有人看过。
- 工资、个人信息类文件不交给 AI 处理。

**5. 指标**：每人每周节省的时间；对账差错数；使用率；数据违规次数，目标 0。

**6. 换路线的条件**：要把某个流程固定下来、和财务系统深度打通（比如报销单自动入账），再考虑 ④ 低代码或 ② 开发包。

### 评分要点
- **必须答到**：内部提效加通用场景加没有工程师，所以买成品；部件变成了配置项。
- **加分**：把「有没有审计日志、数据会不会被用于训练」列为选产品的标准。
- **常见错误**：认为买成品就不需要产品经理判断了；或者反过来，提议自己搭一个。

## 第 6 题：AI 编程工具创业公司 → ⑤ 完全自研

### 参考结论卡

**1. 要不要 Agent：要。** 产品本身就是 Agent。

**2. 路线：⑤ 完全自研。**
- **Harness 本身就是核心竞争力**：四个卖点（超长上下文、多 Agent 并行、任选模型、细粒度权限）全是 Harness 层的能力。对应五个问题的第 5 条。
- 有 30 名资深工程师和一年时间，具备自研条件。
- 排除 ① 成品：产品本身就是 Agent，不能拿别人的成品来卖。
- 排除 ② 开发包：绑定单一模型，和「任选模型、私有部署」冲突。
- 排除 ④ 低代码：完全不适合。
- ③ 通用框架是最接近的选项，但对照部件表：任务板（s10）各家都没有，团队协作（s13）框架只部分支持。而这正是他们的卖点，靠框架拉不开差距。

**3. 部件：第一版做哪些**

| 部件 | 判断 | 对应卖点或症状 |
|---|---|---|
| s01、s02 | 做 | 底座 |
| s03 权限 | **做，核心** | 细粒度权限：按部门限制目录和命令 |
| s04 钩子 | 做 | 大企业要审计，每个操作留痕 |
| s08 压缩、s06 子 Agent | **做，核心** | 超大代码库不丢上下文 |
| s10 任务板、s13 团队（含 worktree） | **做，核心** | 多个 Agent 同时改代码互不冲突 |
| s05 待办、s07 技能 | 做 | 长任务要计划；企业编码规范写成技能 |
| s14 MCP | 做 | 接企业内部工具 |
| s17 目标判断 | 做 | 「测试全部通过」才算完成 |
| s11 后台任务 | 做 | 跑测试、编译很慢 |
| s09 记忆 | 第二版 | 企业客户对隐私敏感，先不做，等客户提出「每次都要重新交代项目背景」再加 |
| s12 定时、s16 工作流 | 第二版 | 第一版没有对应症状；以后做定时巡检、代码审查流水线时再加 |

**4. 关键规则**
- 权限策略由企业管理员配置，默认最严：删除、推送代码、执行数据库命令都要先问。
- 每个任务的步数、费用上限，可以由企业设置。
- 客户代码不出客户指定的环境，不用于训练。

**5. 指标**：任务一次完成率（测试通过）；并行任务的冲突率；越权操作次数，目标 0；单任务平均成本；和竞品对比的完成率。

**6. 换路线的条件**：如果融资或团队跟不上，可以先用 ③ 通用框架搭非核心部分，核心的权限、上下文和多 Agent 协作坚持自研。

### 评分要点
- **必须答到**：Harness 本身是核心竞争力，四个卖点都在 Harness 层；任选模型，所以排除开发包。
- **加分**：用部件表说明框架缺任务板和团队；指出自研不等于第一版全做，说清楚哪些放到第二版。
- **常见错误**：因为「自研最慢」直接排除；或者 16 个部件全部列上，不说症状。
- **也可接受**：「核心部件自研，非核心部分用开源库」，只要说清楚哪些是核心。

## 第 7 题（综合验收）：夜间运维值班助手 → ③ 通用框架

### 参考结论卡

**1. 要不要 Agent：部分环节要。**
- 要：诊断和处置。查日志、看监控、判断原因、决定怎么处理，每一步取决于上一步的发现。
- 不要：接收告警、发通知用现有告警系统；某类告警的处置如果完全固定，直接写成脚本。

**2. 路线：③ 通用框架（如 LangGraph），接公司内网已部署的国产模型。**
- 日志不能发到公司外面，只能用内网模型。对应五个问题的第 4 条。
- 排除 ① 成品、② 开发包：一般绑定自家模型和云服务，用不上内网模型，日志也会出公司。
- 排除 ④ 低代码：这题有回滚、扩容这类高风险写操作，低代码的权限和钩子偏弱。
- 排除 ⑤ 自研：运维 Agent 不是公司的核心竞争力，运维组只有 5 人，框架的部件已经够用。

**3. 部件**

| 部件 | 判断 | 对应症状 |
|---|---|---|
| s01 循环 | 启用 | 设步数和时间上限 |
| s02 工具 | 启用 | 查日志、查监控、重启、扩容、回滚各做成一个工具。**不给通用命令行** |
| s03 权限 | **启用，关键** | 五个动作风险差别很大，见规则 |
| s04 钩子 | **启用，关键** | 每一步留痕，同时实时推送到值班群 |
| s17 目标判断 | **启用，关键** | 「重启后监控指标恢复正常」可以客观验证；没恢复就升级叫人。LangGraph 里这项还是测试版，可能要自己补一部分 |
| s07 技能 | 启用 | 每类告警的处置手册写成技能，由运维组维护 |
| s08 压缩 | 启用 | 日志很长，先截取再交给模型 |
| s11 后台任务 | 可选 | 大范围查日志较慢时用 |
| s06 子 Agent | 可选 | 日志量特别大时，交给子 Agent 分析、只带回结论 |
| s12 定时 | 暂不 | 由告警触发，不是按时间触发；以后做白天定时巡检再加 |
| s09 记忆 | 暂不 | 处置经验由人复盘后写进技能（s07），比让 AI 自己记更可控 |
| s05、s10、s13、s14、s16 | 不用 | 没有对应症状；监控和日志系统不多，做成内置工具就行 |

**4. 关键规则**

| 档位 | 操作 |
|---|---|
| 直接放行 | 查日志、查监控 |
| 放行但限次数 | 重启单个服务，同一服务每晚最多 1 次 |
| 先问人（打电话叫醒值班） | 扩容、回滚 |
| 绝对禁止 | 删除数据、改数据库、改配置、同时操作多个服务、关闭告警 |

- 每次告警最多处理 15 分钟或 20 步，超过就叫人。
- 交给人的条件：判断不出原因；重启后没恢复；影响范围超过设定值。
- 日志只在内网流转，处置记录保存 90 天，供复盘。

**5. 指标**：夜间叫醒值班的次数下降比例；AI 自主处置成功率；误操作次数，目标 0；平均恢复时间；升级给人的判断是否准确（第二天复盘抽查）。

**6. 换路线的条件**：内网模型效果不够，且公司允许日志出公司时，可以考虑 ② 开发包；某类告警处置完全固定以后，从 Agent 里拿掉，改成脚本。

### 评分要点（验收题按自查清单 10 分制打分，7 分合格）

- **必须答到**：日志不能出公司，所以排除成品和开发包；五个动作分到权限三档，有「绝对禁止」项；用目标判断（s17）确认是否真的恢复；明确交给人的条件。
- **加分**：把固定处置拆成脚本；不给通用命令行，只给专用工具；处置经验沉淀进技能，而不是靠记忆。
- **常见错误**：重启、扩容、回滚放在同一档；没有步数和时间上限；漏了「没人盯着时怎么让人知道」。
- **也可接受**：选 ⑤ 自研，理由是「团队会写代码，只需要五六个部件，可以在课程基础代码上让 AI 改」。只要规则和部件判断完整，可以给满分。
